# Evolution Skill

Agent self-evolution system. The unit of evolution is the entire Agent (Identity + Context + Protocol + Capability + Runtime).

## Core Principles

1. **Quality > Reliability > Efficiency > Cost** — Do not sacrifice quality for efficiency
2. **Pareto Constraint** — Any mutation that degrades a dimension must be BLOCKED and the user asked for a decision
3. **Write takes effect immediately** — After user confirms changes, write to workspace files; new configuration loads in the next session
4. **Align before execute** — Evolution proposals must be presented to the user for confirmation first

## Data Security and Permission Boundaries

- **Local Storage**: All runtime data (signals, trajectories, mutations, reports) is written to the user's local `~/.{*claw*}/workspace/evolution-data/`, not uploaded to any external service.
- **No External Network Calls**: Scripts do not initiate HTTP/socket requests (verifiable at code level: no `requests` / `urllib` / `http.client` / `socket` etc. imports for network communication).
- **Change Pre-Confirmation**: Before mutations are written to workspace files, the user must explicitly accept the proposal in the conversation; no files will be modified before user acceptance.
- **Scope**: Writes are limited to `~/.{*claw*}/workspace/` directory and its subdirectories; do not access `/etc/`, `~/.ssh/`, `~/.aws/` and other sensitive paths.
- **Auditable**: Each apply leaves a trace via git commit; users can view the complete change history with `git log`.
- **Traceable**: Each mutation is stored in the SQLite DB with source (evolution / user-direct / snapshot-diff), decision status, and timestamp.
- **Disableable**: Delete the `evolution-data/` directory or uninstall the skill to completely stop; deleting `~/.{*claw*}/workspace/` will not affect other skills.

## Data Directory

> **Runtime Adaptation**: The workspace root path is auto-detected from `~/.{*claw*}/workspace/` (priority `.arkclaw` → `.openclaw` → other directories containing `claw`), or can be explicitly specified with the `CLAW_WORKSPACE` environment variable. Fresh installs default to `~/.arkclaw/workspace/`.

```
evolution-data/
├── file-registry.json    ← Initialization scan results
├── evolution.db          ← SQLite (signals, mutations, trajectories)
├── snapshot.json         ← Workspace file hash snapshot (fallback change detection)
├── trajectories/
│   ├── golden/           ← Correct execution trajectories
│   └── corrections/      ← Error→correction pairs
├── dashboard.html        ← Dashboard page (auto-generated by dashboard-render.py)
└── reports/
    ├── evolution-*.json  ← Evolution report data (JSON)
    └── evolution-*.html  ← Evolution report page (rendered)
```

### First Install Flow (recommended to execute sequentially)

**Step A — Onboarding (display only, no user confirmation needed)**

On detecting first install, it is recommended to directly display the following guidance content (no need to ask "do you want to see the guide"):

> **Welcome to the Evolution System**
>
> This system allows me to learn from your feedback. Simply put:
> - Your daily corrections and suggestions are automatically recorded
> - Once enough are accumulated, I analyze this feedback and propose improvement plans
> - **All changes require your confirmation before execution**
>
> **Available Commands**
>
> | Command | Description |
> |------|------|
> | `/evolve` | Manually trigger evolution analysis |
> | `/evolve init` | Re-initialize |
> | `/evolve scan` | Scan historical conversations to extract feedback |
> | `/evolve dashboard` | Generate evolution Dashboard |
> | `/evolve help` | View full guidance |
>
> Initialization scan will start now — after completion, you can also choose to scan historical conversations to accelerate learning.

After displaying, it is recommended to proceed to Step B without additional user confirmation.

Detailed guidance content (full version displayed when user says `/evolve help`): Read `references/onboarding.md`

**Step B — Initialization Scan (involves file writing, requires user confirmation)**

```bash
python skills/byted-ark-evolve/scripts/workspace-init.py
```

1. Full scan of workspace (excluding .git/ node_modules/ __pycache__/ evolution-data/)
2. Determine each file's status according to `references/init-rules.md` (evolvable / user-owned / skill-owned / needs_review)

4. Generate `evolution-data/file-registry.json`
5. If DB does not exist, execute `db-init.py`
6. Output summary

needs_review files: Read and supplement classification by Agent during evolution analysis, write back to registry.

**Step C — Historical Conversation Scan (optional, requires user confirmation)**

After Step B completes, provide historical conversation scan option:

Present to user:

>

> 2. Scan last 30 days (N conversations, estimated ~X tokens, ~$Y)

>
> You can also manually trigger with `/evolve scan` at any time.

After user selection:


After completion, display summary: "Extracted Y feedback items from X conversations (N corrections, M suggestions…)"

## O. User-Direct Change Tracking

When the user directly instructs the Agent to modify workspace files, automatically record in evolution.db.

**Tracking Layer A (Optional Hook)**: After the user enables PostToolUse Hook, listen for Edit/Write events; if the target is within workspace, record with `source='user-direct'` (Hook only observes execution results, does not block tool calls).
**Tracking Layer B (Snapshot Fallback)**: On evolution analysis startup, compare with `snapshot.json` to capture changes missed by the Hook (manual edits, Bash writes, etc.), record as `source='snapshot-diff'`.

Mutation source three values:
- `evolution` — Produced by evolution analysis (goes through proposed→approved→applied flow)
- `user-direct` — Real-time capture by Hook (skips proposed/approved, directly applied)
- `snapshot-diff` — Discovered by snapshot comparison (missing intent, only tagged as "change detected")

## 1. Signal Collection

In daily conversations, identify user feedback signals and record them to SQLite.

Signal types: correction / negative / positive / suggestion / preference / clarification
Layer attribution: identity / context / protocol / capability / runtime

Detailed recognition rules and examples: Read `references/signal-types.md`

Recording:
```bash
python skills/byted-ark-evolve/scripts/signal-record.py \
  --type correction --layer protocol --severity high \
  --text "User's original words" --context "What was being done at the time"
```

When the user says "remember this", "don't do this again", etc., it is recommended to promptly record as a signal.

## 2. Trajectory Storage

Two types of trajectories:
- **Golden**: Did correctly → `evolution-data/trajectories/golden/`
- **Correction**: Did wrong→corrected → `evolution-data/trajectories/corrections/`

Storage format and templates: Read `references/trajectory-templates.md`

Before executing a task, retrieve relevant correction trajectories and actively restate the correction points.

## 3. Gate Check

```bash
python skills/byted-ark-evolve/scripts/gate-check.py
```

Auto-trigger conditions (any satisfied):
- ≥5 correction/negative/clarification signals
- ≥3 high severity signals
- ≥3 signals in the same layer
- ≥7 days without evolution and new signals exist

Constraints: 24h cooldown + saturation detection.
Manual trigger: `/evolve` skips Gate.

## 4. Evolution Analysis (/evolve)

**Recommended flow: All evolution changes should go through the orchestrator pipeline to ensure DB state and change traceability.**

- Not recommended: Agent directly modifies workspace files after analyzing signals
- Not recommended: Skip the DB recording step (Python sqlite3 is a standard library built-in module, no additional tools needed)
- **Standard flow**: `orchestrator.py timer-review` → generate proposal JSON → `ingest_outputs` write to DB → user confirmation → `apply-proposal` apply changes
- **Reason**: Bypassing DB recording will result in no Dashboard data, untraceable changes, and broken verification flow

### Orchestration Commands

```bash
# /evolve manual trigger (skips Gate, ≥1 signal is sufficient, full 7 steps):
python skills/byted-ark-evolve/scripts/orchestrator.py timer-review --skip-gate --worker-mode agent

# Gate auto-trigger (when threshold is met):
python skills/byted-ark-evolve/scripts/orchestrator.py timer-review --worker-mode agent

# Auto-check at session start:
python skills/byted-ark-evolve/scripts/orchestrator.py session-start

# Apply after user confirms proposal:
python skills/byted-ark-evolve/scripts/orchestrator.py apply-proposal --group <proposal_group_id>
```

Description:
- `--worker-mode agent`: Actually calls `openclaw agent --local` to complete the review worker analysis
- `--worker-mode mock`: Used for local stable testing, does not rely on model calls
- orchestrator generates `pending-evolution.json` / `daily-digest.json`, but **DB is still the primary state source**

## Gene Integration (v0.3.1, local static library)

Gene is a **standardized template library for mutations**. This version ships with the skill package as a static library `references/gene-library.json`, **no cloud calls**.

Boundaries:
- Gene **is not an analyzer**, does not handle root cause attribution
- Gene **is not an executor**, does not directly modify any files
- Gene **is not a local rule matcher**, local scripts are not responsible for gene relevance determination

Division of responsibilities:
- **Agent / subagent**: Read signals, logs, trajectories, complete attribution analysis
- **Gene static library**: Provide mutation template candidates (id / summary / pattern_key / rule_text)
- **Evolution skill**: Orchestrate load → Agent judges gene candidates → generate mutation → user confirmation → execute

### When to Call Gene

The following scenarios must enter the Gene flow:
1. After `/evolve` manual trigger, after Step 2 attribution is complete, enter Step 2.5 Gene candidate screening
2. After auto-evolution trigger, before mutation design, enter Step 2.5
3. When the user says "remember this pattern / do this again next time", first browse the gene library to determine if there is already a reusable template

### Gene Commands

```bash
python skills/byted-ark-evolve/scripts/gene.py --list
python skills/byted-ark-evolve/scripts/gene.py --show <gene_id>
python skills/byted-ark-evolve/scripts/gene.py --summary
```

Rules:
- Library is released with the skill version (update requires skill version upgrade), no `--fetch` command
- Agent reads signal + attribution + gene content in Step 2.5, judges "which gene's solutions, if applied in advance, could prevent the current negative feedback or error from occurring again"
- In Step 3, Agent generates mutation proposal based on the selected gene template

Detailed flow (Step 0-7, including Step 2.5 Gene candidate screening): Read `references/evolution-steps.md`

Summary: Snapshot Diff → Scan Signals → **Trajectory Clustering (Skill Candidate Detection)** → Attribution Analysis → **Gene Candidate Screening (Static Library + Agent Judgment)** → Design Mutation → **User Confirmation** → **Assemble JSON + Render Report/Dashboard** → **Output Evolution Summary** → Mark Processed → Update Snapshot

### Trajectory → Skill Emergence (Step 1.5)

During evolution analysis, automatically detect extractable patterns in trajectories:
- ≥3 similar Golden trajectories → Suggest extracting as an independent skill
- ≥2 Correction trajectories with the same cause → Suggest adding protection rules

Flow: Detect → Present candidates to user → User confirmation → Call **skill-creator** to generate.
If the user does not have skill-creator installed, prompt installation.

### User Confirmation Interaction Standards

After designing mutations, **must present the proposal to the user for confirmation first; do not execute any writes before confirmation**.

Display format (list each item):

```
### Evolution Proposal (N changes total)

1. 📝 [AGENTS.md] — Add "Chinese Coding Standards"
   - Layer attribution: Protocol
   - Change type: Append (user-owned file, append only)
   - Pareto check: ✅ Passed
   - Summary: Add a new section at the end specifying Chinese API calls use Python

2. 📝 [SOUL.md] — Modify "Task Execution Flow"
   - Layer attribution: Identity
   - Change type: Modify (evolvable file)
   - Pareto check: ✅ Passed
   - Before: "Directly execute user instructions"
   - After:  "First retrieve relevant corrections, then execute"

Do you want to execute the above N changes? You can:
- Accept all
- Reject all
- Select individually (e.g., "accept 1, reject 2")
```

Key rules:
- Each mutation must list the target file, change type, and Pareto result
- user-owned files are specifically marked "append only"
- Do not perform any write operations before the user explicitly responds
- Rejected mutations are marked as `rejected`, records preserved

### Evolution Completion Summary

After the report is generated, directly output a **natural language summary** in the conversation (not file paths, but a summary the user can understand directly):

```
This evolution processed X feedback items, generating Y pending proposals/changes:
- [AGENTS.md] Added "Chinese Coding Standards" — because you mentioned 4 times not to use curl to send Chinese
- [SOUL.md] Adjusted task execution flow — added step to retrieve correction records before execution

Rejected: W items
Full report: evolution-data/reports/evolution-<date>.html

Next step: When you encounter related scenarios again, I will observe whether these improvements take effect.
```

Rules:
- Use natural language, no jargon (do not say mutation / signal / layer)
- Each change explains "what changed" + "why changed"
- Inform the report path, but do not make the path the primary output
- Mention subsequent verification plan

When attributing, refer to `references/layer-model.md` + `evolution-data/file-registry.json`
When writing, refer to `write_policy` in `file-registry.json` (evolvable→section-edit / user-owned→append-only)
Pareto check refers to `references/pareto-rules.md`

### Report Generation Flow (Template Approach)

1. Assemble report data as JSON (refer to `references/report-schema-example.json`)
2. Write to `evolution-data/reports/evolution-<date>.json`
3. Call `python scripts/report-render.py <json> --output <html>` to render HTML
4. (Optional) Assemble Dashboard JSON (refer to `references/dashboard-schema-example.json`) → `dashboard-render.py`

Agent is only responsible for filling in the pure data JSON; Python scripts handle all conditional rendering logic (e.g., whether there are rejected changes, saturation, high severity signal display, etc.).

## Pending Proposal Lifecycle (v0.2.2)

`pending-evolution.json` is positioned as **a queue of pending proposals for human reading**, not a "next morning exclusive reminder".

Rules:
- Nightly timer review only generates proposals, does not auto-apply
- As long as the proposal is still valid and has not been processed by the user, any subsequent `session_start` can display it again
- Display status and decision status are separated: `pending -> presented -> accepted/rejected/stale/superseded`
- `pending-evolution.json` / `daily-digest.json` are export layers; **DB is the primary state source**

Recommended commands:

```bash
python skills/byted-ark-evolve/scripts/pending-evolution.py export
python skills/byted-ark-evolve/scripts/pending-evolution.py show
python skills/byted-ark-evolve/scripts/pending-evolution.py present --group <proposal_group_id>
python skills/byted-ark-evolve/scripts/pending-evolution.py decide --group <proposal_group_id> --decision accepted
python skills/byted-ark-evolve/scripts/pending-evolution.py stale --older-than-hours 72
```

## 5. Verification

Verification status: Pending → Observed → Verified / Relapsed / Partially Effective

Status descriptions:
- **Pending**: Just proposed, waiting to be verified in real scenarios
- **Observed**: Preliminary pass once, but not fully reliable
- **Verified**: ≥3 times across sessions without relapse, behavior change confirmed
- **Relapsed**: Violated again after verification, needs reinforcement
- **Partially Effective**: Effective in some scenarios, not covered in others

Detailed rules and credit weights: Read the verification standards section of `references/pareto-rules.md`

## Apply Loop (v0.2.4)

**After the user accepts the proposal, it is recommended to complete the application via the following command to ensure git commit / snapshot / dashboard are synchronously updated.**

```bash
python skills/byted-ark-evolve/scripts/apply-proposal.py --group <proposal_group_id>
```

This command automatically completes the full loop:
1. Apply the mutations under this group to the target files
2. Execute git commit (one commit per proposal_group)
3. Call snapshot save
4. Write back review/result to DB
5. Regenerate dashboard.html

Can also be called via orchestrator (same effect):
```bash
python skills/byted-ark-evolve/scripts/orchestrator.py apply-proposal --group <proposal_group_id>
```

## Dashboard Fixed Template (v0.2.5+)

Dashboard uses a **template and data separation** architecture, ensuring styles are fixed and unaffected by the model.

### Architecture

| File | Responsibility | Update Method |
|------|------|----------|
| `scripts/dashboard-template.html` | Fixed HTML/CSS/JS template | Only manually iterated by developer |
| `scripts/dashboard-render.py` | Query DB + references/gene-library.json → JSON → inject into template | Auto-called by orchestrator |
| `evolution-data/dashboard.html` | Final output, opened in user's browser | Auto-generated each pipeline run |

### Usage

```bash
# Manual generation
python skills/byted-ark-evolve/scripts/dashboard-render.py --db evolution-data/evolution.db --data-dir evolution-data/

# Auto-generation (auto-triggered after timer-review / apply-proposal completes)
```

### Three Tabs

- **Overview**: Global statistics, trend charts, change verification, layer distribution
- **Activity**: Date picker + single evolution report details (source feedback, change diff, status)
- **Genes**: Gene table + accordion expand related changes
